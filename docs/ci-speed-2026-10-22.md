## First implementation: repeated Tier 2 setup

Across 59 successful concrete test jobs, checkout took median 10 seconds
(range 8–12), bootstrap installation 15 seconds (9–87) and the full package
installation 34 seconds (28–49). Samples include PR, queue and master work;
this is not a controlled runtime estimate.

Test-only runners unpack a tree whose configure, source compilation and
symbol comparison already passed in the build job. They do not need full
Git history or browser/websocket source downloads. Use a normal shallow
checkout there; retain recursive submodules and full history in the builder.
The harness initializes those submodules only when building. Complete OFF/ON
CTest registries and all runtime package inputs remain unchanged.

Both fresh containers already refresh apt indexes before installing Git.
Reuse those same indexes in their later package install instead of refreshing
them a second time. Package caching, install retries and fail-on-error remain.

## Rust execution: schedule across existing binaries

The [local experiment](ci-evidence/2026-10-22-rust-runner-experiment.json)
separates a 41.48-second initial no-run compilation from a subsequent
96.34-second Cargo suite command. The latter reported only 0.29 seconds
build work, then ran the eight category executables sequentially. Core,
application and utility execution took 29.27, 29.85 and 18.79 seconds.
A linker-only diagnostic, using the original `cc` behind a timing wrapper,
recorded 35 calls totaling 2.17 seconds of link wall time (overlapping calls;
not gate elapsed). Individual links were at most 0.21 seconds. Changing the
linker identity triggered a diagnostic rebuild, so its 18.15-second outer
command is not an A/B compilation result. These local measurements do not
justify changing linker settings or bypassing cache freshness safeguards.

The candidate uses pinned nextest 0.9.143 on Linux x86-64/aarch64 to schedule
individual tests globally across the same eight binaries. It caps concurrent
tests at four or the available CPU count, whichever is smaller. It builds no
additional Rust test executable, changes no assertion and uses the same
selected packages. Other hosts retain Cargo's existing execution path.

Nextest does not run documentation tests; Cargo runs them separately, even
when a unit suite fails. Both results must pass. The repository's explicit
runner configuration selects all tests, with no retry-to-green; user runner
configuration is disabled. Existing ignored tests retain their status.
An empty workspace is an error; a scoped package with no tests retains
Cargo's existing successful zero-test behavior. The source-freshness probe
now has an actual assertion to exercise this runner before the unchanged
nested-source mutation must fail compilation.

The static upstream archive is SHA-256 pinned and checked before installing
or reusing its executable; unsupported hosts download nothing. Installation
happens only when Rust scope selects tests. No new remote cache writer or
workflow file is added. Runner code/configuration participates in Rust lane
keys, attestation surfaces and workspace scope selection, so changing the
executor cannot reuse an old proof or skip its runtime qualification.

### Expected gain before rollout

| Observation | Cargo | Pinned nextest plus Cargo doctests |
| --- | ---: | ---: |
| Local warm suite command, one trial each | 96.34 s | 64.89 s |
| Passing unit cases | 2,019 | 2,019 |
| Existing ignored case | 1 | 1 |
| Passing documentation cases | 4 | 4 |
| Rust category executables | 8 | 8 |

Cargo discovery was compared by exact passing-case identity across all eight
categories; the only unexecuted discovered case is the existing ignored NVENC
real-GPU test. A separate GNU-binary prototype took 64.18 seconds without
doctests; do not pool it with the complete musl candidate.

The complete local observation is 31.45 seconds shorter, about 32.6%. This is
one warm-tool sample on a local host with Soldr 0.9.34, while CI pins 0.9.38;
it is not an expected whole-gate percentage. Fresh hosted tool download cost,
CPU contention, changed-crate scope and critical-path overlap must be measured.
Use 0–31 seconds as a planning range for this Rust execution phase until CI
qualification; overlap can make gate savings zero. Retain conditional cook
profiles and wrapper/fingerprint safeguards. PR/queue runtime qualification
and the representative post-rollout day remain outstanding.
## Fresh prepared-environment transfer protocol (#1592)

The opt-in `tier2-setup-probe` input on the existing Pull workflow is restricted
to manual master runs. It preserves the normal full build. The final gate includes the optional jobs;
a requested experiment failure fails that manual run. On PRs and queue events,
both experiment jobs are skipped.
It requires the runtime manifest shipped by #1707; do not dispatch until that
change is on master. No new workflow, registry publication, token permission or
remote cache writer is introduced.

One disposable producer installs the actual artifact's exact package closure
on the pinned stock Ubuntu base, retaining checkout bootstrap tools. It records
the complete resolved dpkg inventory, immutable image ID, input pins, compressed
archive SHA256/bytes, revision and pull/install/commit/save/compression durations.
The image and metadata are separate one-day Actions artifacts. Capture the
producer's input download, apt restore and artifact upload step durations too;
these are publication cost, not free savings.

Three fresh stock consumers restore the existing apt archive family and install
the complete locked producer inventory. Three prepared consumers download,
verify, decompress and load that exact image, rejecting a resident prepared
image and inventory drift. Stock consumers download only the small metadata,
so image transfer is not charged to both variants. Join Actions download/restore
step durations with JSON phase durations; neither phase sum alone is total setup.
The stock comparison uses one package transaction rather than CI's separate
bootstrap/install transactions, so report that modeling limit. Record cache hits
and misses from Actions rather than assuming the cache restored.

The first prepared consumer additionally runs both complete OFF/ON suites with
the existing harness and unchanged C tests, at the original artifact paths.
Those logs are retained separately from setup measurements. An experiment pass
is not a lane attestation and cannot skip normal coverage. The manual experiment
uses seven extra runners and does not make its producer part of routine CI.

Before dispatch, expected net benefit is unknown: the historical package-install
portion was 28–49 seconds, but runtime closure reduction changes that baseline,
and archive download/load/verification plus amortized producer cost may consume
all of it. Retain stock setup unless the fresh measurements, coverage and normal
CI provide evidence for a separate deployment decision. Report rejected results
and small-sample variance; do not promise a universal gate percentage.
## Runtime package closure experiment (#1694, #1592)

The builder retains the full development package set. Test runners consume an
exact-version manifest produced from every runtime ELF in the built tree with
`ldd` and `dpkg-query`, plus explicit dlopen providers and tools. Missing loader
libraries or package metadata fail closed. The manifest travels inside the
existing artifact; apt archive restore and master-only publication stay intact.

Local bosn validation used the actual #1700 hosted artifact (run 39711866137,
189,868,667 compressed bytes) at its original absolute paths in the pinned
Ubuntu 26.04 environment. The reduced manifest contained 224 direct package
specifications. Both complete suites used unchanged C tests, Xvfb and the
existing isolation policy:

| Mode | Registered | Executed | Device skips | Failures | CTest seconds |
| --- | ---: | ---: | ---: | ---: | ---: |
| OFF | 353 | 350 | 3 | 0 | 190.63 |
| ON | 353 | 350 | 3 | 0 | 166.96 |

The same Pulse monitor/restart/two-source cases skipped. An initial prototype
was rejected because it lacked the compiler/Ninja needed by the manifest CMake
fixture and the unversioned VLC loader library. Retaining gcc, libc6-dev,
ninja-build and libvlc-dev restored fixture execution and VLC coverage; focused
regressions now require them. Test runners do not configure OBS, but this
unchanged CTest fixture does compile a small C program.

Local Docker-reported `Size` changed from 541,093,691 to 445,476,013 bytes
(17.7% smaller), using the containerd snapshotter. These fields are not verified
uncompressed rootfs sizes or wire-byte counts. This compares package closure, not fresh hosted transfer or
setup latency. Expected setup saving is bounded by the old package installation
portion (baseline 28–49 seconds), with manifest generation and artifact handling
subtracting from any gain. No gate saving is claimed before hosted comparison.
A fresh prepared-image transfer experiment and the post-rollout observation day
remain separate requirements.

### Remaining serial CTest decision

The complete-suite evidence identifies `test_deinterlace_2x_field_order` at
82.60 seconds OFF and 82.88 seconds ON. Inspection of the unchanged test explains
nearly all of that wall time: 40 cases, 16 at source 30 fps and 24 at 25 fps.
Each case sends six warmup frames and 36 measured frames on real timestamps,
then waits 300 ms to drain playback and 250 ms between cases. The first frame
is immediate, so its intended pacing/drain floor is:

`16 × (40 / 30 + 0.55) + 24 × (40 / 25 + 0.55) = 81.733 seconds`.

That is 98.6–99.0% of these observed durations, before accounting for startup,
video resets or additional warmup polling. This is source-derived wall-time
attribution, not a CPU sampling result. The rest of each complete suite is
already scheduled with CTest concurrency and retained cost history; the
runtime evidence records every individual duration for further comparison.

Decision: reject a deinterlace scheduling/algorithm change for this batch.
There is no demonstrated substantial removable computation here. Preserve all
frame-rate/order cases, assertions, real-time pacing and `RUN_SERIAL`; no C test
or public header changes. Do not add its duration to setup/Rust savings, and do
not restore shards. Revisit only if separate profiling establishes a removable
cost while preserving the same real-time correctness coverage and isolation.

### Manifest producer overhead

The first hosted producer took 13.36 seconds to derive its runtime manifest.
A follow-up local cProfile comparison in the same full Ubuntu environment
measured 14.562 seconds before and 7.663 seconds after batching package ownership
queries. The original performed 850 subprocess calls; the candidate performed
621. Package ownership resolution dominated the removed work. Per-path lookup
remains for missing records and loader aliases/diversions, and unresolved
ownership still fails closed. The 224-pin output is byte-for-byte identical.

These are single sequential local profile runs, not a hosted A/B distribution.
The expected additional opportunity is approximately 0–7 seconds of producer
work; the actual hosted result and critical-path overlap remain to be measured.
Normalized function timings and the matching manifest SHA256 are retained in
the runtime experiment evidence. No full-suite assertion or dependency changes
are introduced by this lookup optimization.
